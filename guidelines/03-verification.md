# 03. 검증·회귀 확인 단계 지침

- 적용: 구현 직후 검증, 새로 들어온 저장소 커밋의 회귀 검증, 단위테스트·화면 시험
- 상위 지침: [`../AGENTS.md`](../AGENTS.md) (공통 규칙이 항상 우선)

## 1. 변경 후 검증 (diff 기준)

- 요청 범위 밖 변경이 없는가
- 기존 로컬 변경을 덮어쓰지 않았는가
- Form 이름·ID·값·전송 파라미터가 유지되는가
- JavaScript 선택자와 이벤트가 유지되는가
- Controller/API URL, 세션과 권한 조건이 유지되는가
- 대상 런타임 및 구버전 브라우저 호환성을 유지하는가
- 공통 자원이 다른 화면에 회귀를 만들지 않는가
- 임시 로그와 디버깅 코드가 남아 있지 않은가
- 여러 줄로 이어 붙인 문자열·SQL 컬럼·배열 목록에 구분자(콤마) 누락이 없는가(다른 개발자 커밋 검토 시에도 확인)

검증 환경(브라우저 종류, OS, 모바일/에뮬레이션, 자동 도구/수동 조작, 콘솔/서버 로그)은 **실제 수행한 항목**과 **미수행·권장 항목**을 명확히 구분한다.

로그인, 본인인증, 권한, 신청/결제, 파일 업로드, 게시판, CMS, 세션, Ajax, 외부 API와 관리자 생성 콘텐츠는 우선 회귀 위험으로 본다.

## 2. 새로 들어온 커밋 회귀 검증

자체 검증을 마친 기준선(리비전/커밋) 이후 들어온 변경 파일이 영향을 주는 화면만 선별해 다시 검증한다.

1. 기준선과 최신 HEAD의 변경 파일 목록을 확인한다(SVN 커밋 메시지에 한글이 있다면 `--xml` 출력으로 깨짐 방지).
2. 변경 파일을 영향도별로 분류한다.
   - **A. 공통 layout·include·CSS·JS, 템플릿 설정, 게시판 스킨**: 해당 영역 표본 화면 전체 재검증
   - **B. 개별 화면 템플릿·화면 전용 CSS·JS**: 그 화면과 이를 포함하는 곳만 재검증
   - **C. 백엔드(Java 등)·SQL·설정(properties)**: 화면 출력이나 동작이 바뀌는지만 확인
3. diff에서 기존 개선 사항(예: 접근성 속성, 안내 문구, 레이블 연결 등)이 유실되지 않았는지 확인한다.
4. 새 마크업이나 스크립트가 프로젝트 구현 규칙을 지키는지 확인한다.
5. 정적 문법 점검(3절)과 해당 화면의 동작 확인을 수행하고, 필요 시 자동 진단 결과를 기준선과 비교한다.

다른 개발자의 커밋을 검토할 때는 기능·품질 회귀 위험 중심으로 보고한다. 사용자가 요청하지 않으면 다른 사람의 커밋 파일을 임의로 수정하지 않는다.

## 3. 정적 문법 점검 도구

커밋 전 정적 점검으로 마크업·스크립트 구문 깨짐을 사전에 차단한다.

- **JSP/태그 속성 따옴표 중첩 검사**: [`../tools/jsp_tag_attr_check.py`](../tools/jsp_tag_attr_check.py)
  - 변경 파일이 검사 경로에 포함되는지 먼저 확인하고 `python tools/jsp_tag_attr_check.py <대상_WEB-INF_경로>`를 실행한다. 대상 경로와 출력된 `hits` 값을 함께 기록한다. [결과 해석과 한계](../tools/README.md)
- **JavaScript 문법 검사**: 수정된 `.js` 또는 인라인 `<script>` 블록에 대해 `node --check`로 구문 오류 증가 여부 확인
- 정적 점검만으로 실행 성공을 단정하지 않는다. 로그인·DB 데이터가 필요한 화면은 실제 실행 환경에서 별도로 확인한다.

## 4. 시험 중 데이터 변경 금지

화면 시험 중 운영/개발 데이터를 바꾸는 조작은 하지 않는다(상세: `AGENTS.md` 4절 '권한과 작업 경계'). 필요한 경우 조회와 유효성 검증 메시지 확인 단계까지만 수행하고, 최종 제출·결제 등 실행하지 않은 항목은 보고에서 구분한다.
