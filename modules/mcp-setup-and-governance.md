# 모듈: MCP(Model Context Protocol) 구성 및 거버넌스

- 적용: 브라우저 자동화(Playwright), 협업 문서(Notion), DB 조회(MSSQL 등) MCP 서버를 연결해 사용하는 환경
- 상위 지침: [`../AGENTS.md`](../AGENTS.md)
- 설정 예시 파일: [`../.mcp.example.json`](../.mcp.example.json)

## 1. 왜 MCP 거버넌스가 필요한가?

MCP를 연결하면 AI가 실제 브라우저, 사내 문서, 데이터베이스에 직접 접근할 수 있어 생산성이 크게 높아지지만, 가드레일이 없으면 다음 위험이 발생한다.

1. **브라우저 세션 오염**: 테스트 중 로그아웃·만료 시나리오가 사용자의 실제 작업 브라우저 세션을 끊어버림
2. **문서 덮어쓰기**: AI가 확인 없이 Notion 페이지를 새로 만들거나 기존 내용을 덮어씀
3. **자격증명 유출**: `.mcp.json`이나 설정 파일에 DB 비밀번호·API 토큰을 평문으로 넣어 저장소에 커밋됨
4. **의도치 않은 데이터 변경**: 조회 목적의 DB/웹 조작 중 데이터 수정(`UPDATE`/`DELETE`/최종 제출)이 실행됨

## 2. 서버별 안전 운영 기준

### 2.1. Playwright MCP (브라우저 자동화 및 접근성·기능 검증)
- **격리 프로필 필수 (`--isolated`)**: 사용자의 기존 브라우저 프로필·쿠키와 분리된 임시 컨텍스트에서 실행해 로그인/세션 충돌을 방지한다.
- **Headless 기본 실행**: 자동 검증 파이프라인에서는 `--headless`를 기본으로 두고, 화면 시각 확인이 필요한 경우에만 별도 캡처로 검증한다.
- **최종 변경 액션 차단**: 테스트 중 결제, 신청 확정, 게시물 삭제 등 DB 상태를 바꾸는 최종 Submit은 누르지 않고 유효성 안내·확인 창까지만 검증한다.

### 2.2. Notion MCP (문서 조회 및 작업 이력 동기화)
- **읽기/쓰기 분리**: 분석·개발 작업 중에는 조회(`fetch`, `search`)만 허용하고, 쓰기(`update`, `create`)는 사용자가 명시적으로 요청했을 때만 실행한다.
- **재조회 검증 루프**: 수정 후 반드시 페이지를 다시 조회해 본문 손실 여부를 검증한다(상세: [`docs-notion-sync.md`](docs-notion-sync.md)).

### 2.3. Database MCP (MSSQL 등 스키마·데이터 조회)
- **Read-Only 원칙**: 테이블 구조, 데이터 정합성, 콘텐츠 메타데이터 확인 등 **읽기 전용 조회(`SELECT`)** 목적으로만 사용한다.
- **쓰기 차단**: AI가 임의로 `INSERT`/`UPDATE`/`DELETE`/`DDL`을 실행하지 않으며, 수정 SQL이 필요하면 스크립트 초안만 제안하고 실행은 사용자가 담당한다.
- **운영 DB 분리**: 가능하면 로컬 또는 읽기 전용 개발 DB 계정만 연결한다.

## 3. 설정 및 보안 관리 원칙

1. **자격증명은 환경변수로만 주입**:
   - 저장소에는 [`../.mcp.example.json`](../.mcp.example.json)처럼 변수 자리표시자(`${NOTION_TOKEN}`, `${DB_PASSWORD}`)만 둔다.
   - 실제 키가 들어가는 `.mcp.json` 및 도구별 로컬 설정(`*.local.json`)은 반드시 `.gitignore`로 커밋에서 제외한다.
2. **도구 권한 최소 허용(Least Privilege)**:
   - 에이전트 실행 설정에서 읽기 도구와 Bash/쓰기 도구의 자동 허용 범위를 구분해, 파괴적 명령이나 외부 쓰기 호출은 사용자 승인을 거치도록 구성한다.
